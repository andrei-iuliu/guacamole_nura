# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this repo is

A bringup workspace for running postmarketOS / Nura on the OnePlus 7 Pro (`oneplus-guacamole`, Qualcomm SM8150 / Snapdragon 855). There is no application code and no test suite. "Testing" means building a `boot.img`, booting it on the phone, and checking `dmesg` or the hardware over SSH (`ssh user@172.16.42.1`, USB gadget networking). `docs/PLAN.md` tracks phase status; audio works for stereo speakers and the internal mic (earpiece/call audio still pending). Battery, charging, Wi-Fi and Bluetooth work. ModemManager detects the modem over the IPA data path, but cellular (SIM, registration, data, calls) is untested: no SIM has been fitted yet.

## Boot image pipeline (actual dev loop)

Device-tree work does **not** go through the upstream `dts/*.dts` sources. The loop is:

1. Edit **`base_guacamole_working.dts`**. This is a *flattened, decompiled* DTS (from `dtc -I dtb -O dts`): no `#include`s, no labels for most nodes, and every cross-reference is a raw numeric phandle (`<0xde>`). When you add a node that others reference, give it a `phandle = <0x...>;` that is unused (grep the file for the current maximum) and reference it numerically.
2. `python3 scripts/patch_dtb.py` applies fix-ups by **exact string replacement** (tab-indented text blocks): it corrects reserved-memory regions, adds the ramoops/bootloader_log/cdsp_sec/param/mtp carve-outs, and injects `qcom,msm-id` / `qcom,board-id` so ABL accepts the DTB. It writes `/tmp/patched_guacamole.dts` and compiles `/tmp/custom_guacamole.dtb`. The `assert` fails if the `rmtfs-mem` block it anchors on is reformatted, so keep that block's exact formatting.
3. `scripts/build_bootimg.sh` runs step 2. It then packs `build/boot.img` (mkbootimg header v2, offsets matching `deviceinfo`, cmdline with ramoops and `PMOS_NO_OUTPUT_REDIRECT`) and adds an AVB hash footer. The kernel comes from `$KERNEL_DIR/boot/vmlinuz`; the default is the newest `build/kernel_rN` directory (it used to be `build/kernel_r6`, and images built with that default on 2026-11-23 silently carried a kernel without the UFS HS-G3 cap, so always check `Using kernel from` in the output). The initramfs comes from `$INITRAMFS` if set, else `$KERNEL_DIR/initramfs`, else `/tmp/device_initramfs_r4` or the pmbootstrap chroot at `~/.local/var/pmbootstrap/chroot_rootfs_oneplus-guacamole`.
4. `scripts/fastboot_boot.sh [boot.img]` runs `fastboot boot` with the recovery the ABL needs (non-destructive; prefer this for anything untested). The phone boots untethered since 2026-11-22: `boot_b` (the active slot, whose `dtbo_b` is zeroed) carries the working `build/boot.img`, so a plain power-on or `reboot` lands in Linux. Once an image is proven with `fastboot boot`, write it with `scripts/flash_boot.sh flash` (which flashes `boot_b`, never `boot_a`: slot a still has its stock DTBO and switching slots would also switch xbl/abl). The stock boot image is `stock_boot_full.img`; `backups/vbmeta_b.img` is the stock vbmeta (verification is still enabled, the unlocked bootloader tolerates the unsigned hash footer). The ABL often stalls at `Sending 'boot.img'` or answers `Load Error` while the device still enumerates; the script then resets the USB device from the host (`USBDEVFS_RESET`), runs `fastboot reboot bootloader` and retries, which clears it without touching the phone. `scripts/flash_boot.sh test` is the plain version; wrap it in `timeout 10`. Reboot into the bootloader with `ssh user@172.16.42.1 'sudo systemctl reboot --reboot-argument=bootloader'` (SSH key auth works; `sudo` needs the test password). The reboot reason reaches the ABL through the PM8150 PON `mode-bootloader`/`mode-recovery` properties and the IMEM `reboot-mode@65c` node in the DTS, and it survives only a warm reset: `guacamole-wlan-down.service` takes `wlan0` down before `rmtfs` stops the modem, because stopping the modem with the WLAN firmware active turns the reset into a hard one and the phone boots normally instead.
5. After a panic, reboot into TWRP and run `scripts/ramoops.sh` to pull pstore logs into `logs/ramoops_<timestamp>/`.

```bash
./scripts/build_bootimg.sh
```

With a new kernel package, the modules in `/lib/modules` on the phone must match the kernel you boot. Install the APK on the phone first (`apk add /tmp/linux-...apk`; this only regenerates `/boot`, it never flashes), extract the same APK into `build/kernel_rN/`, copy the phone's new `/boot/initramfs` next to it, and then run:

```bash
KERNEL_DIR=$PWD/build/kernel_r8 INITRAMFS=$PWD/build/kernel_r8/initramfs ./scripts/build_bootimg.sh
```

```bash
./scripts/flash_boot.sh test
```

Needs on the host: `dtc`, `mkbootimg`, `avbtool`, `fastboot`/`adb` (or `pmbootstrap flasher` as a fallback).

`base_guacamole_working.dts.bak` and `.adsp_only` are untracked manual snapshots from before audio changes. They are not inputs to the build.

## Kernel and packages

- `device/testing/*` are pmaports packages. pmbootstrap builds from `~/.local/var/pmbootstrap/cache_git/pmaports/device/testing/`. The device and firmware packages there are symlinks to this repo, but `linux-postmarketos-qcom-sm8150` is a **separate copy**. After editing the repo copy, copy the files there and run `pmbootstrap checksum`; then make sure both directories are identical (`diff -rq`). Never run two pmbootstrap commands at once: `checksum`/`build` wipe the shared build dir (`chroot_native/home/pmos/build`), which kills a build already in progress. Packages: `device-oneplus-guacamole` (deviceinfo, the charging daemon `guacamole-chgctrl`, the MPSS init script, WoWLAN configs), `firmware-oneplus-guacamole`, and `linux-postmarketos-qcom-sm8150`. The kernel is the `v6.17.0-sm8150` tag from gitlab.com/sm8150-mainline/linux, built with `LLVM=1` and carrying the local `000N-*.patch` files.
- `scripts/build_kernel.sh /path/to/linux` builds a kernel tree via pmbootstrap `envkernel.sh` and then runs `pmbootstrap build --envkernel`. Source `scripts/envsetup.sh` for the `pmb` / `pmb-guacamole` / `envkernel` helpers.
- `pmbootstrap/` is a gitignored clone of pmbootstrap. The pmbootstrap work dir is `~/.local/var/pmbootstrap`.
- Kernel patches: `0004` DSC panel + MSM DSI 2-slices-per-packet, `0005` s6sy761 reset GPIO, `0006` geni I2C FIFO mode, `0007` TFA9874 speaker amp driver (ported from hotdog), `0008` SM8150 `QUATERNARY_MI2S_RX` speaker backend + per-SLIMbus-link channel maps, `0009` ath10k quiet-mode skip, `0010` UFS HS-G3 cap, `0011`/`0012` charger and gauge fixes, `0013`–`0016` IPA v4.1 (SM8150) support for the modem data path (from hotdog 0144/0145/0156), `0017` FastRPC sensors-PD message buffers from the reserved pool (hotdog 0148), `0018`/`0019` SMB5 USB3 SDP current and the writable `input_current_limit` property (hotdog 0151/0152), `0020`–`0024` USB-PD on PM8150B: input window override, Type-C sink exit on CC only, charger following the TCPM contract (current, standby, voltage window), VBUS diagnostics. The board never passes a 9 V PD supply to the PMIC (USBIN reads 0 V under a 9 V contract), so the connector sinks 5 V/3 A only; do not re-add the 9 V/12 V PDOs without new evidence. `0025`–`0045` the hotdog camera series (SM8150 CAMSS with C-PHY, S5K3M5/IMX586/IMX481/IMX471 sensors, LC898217XC and AK73xx lens drivers) with hotdog's board DTS hunks stripped, `0046` camss parks the VFE required-opp vote while a domain is off, `0047` upstream drm/msm fix for freeing imported dma-bufs, `0048` arms the APSS watchdog at probe (debug aid: a dark hang bites after 30 s), `0049` re-notifies TCPM once a decaying VBUS has reached vSafe0V (without it, swapping the PC cable for a DisplayPort adapter left the port in `SRC_ATTACH_WAIT` forever and the adapter never attached; the same stall hit the sink direction when swapping back). Since r31 `CONFIG_DRM_MSM` and the DSC panel driver are modules: with the DisplayPort controller enabled, the built-in display stack hung the boot in about one boot out of two (silent, no watchdog bite, Power held 10 s to recover), while the module loaded at udev coldplug (about 14 s) bound cleanly in 12 of 12 boots. The race itself is not understood; the lockup detectors (`CONFIG_SOFTLOCKUP_DETECTOR`, `DETECT_HUNG_TASK`, `HARDLOCKUP_DETECTOR` since r29) never fired on it. The initramfs carries no display module, so the panel lights at about 14 s and there is no early splash.

## Reference material (untracked, read-only)

- `hotdog-linux-bringup/`: a bringup project for the OnePlus 7T Pro (`hotdog`), a sibling device. Useful for SM8150 patterns, but its hardware differs (for example, touch power on hotdog comes from PM8150L; on guacamole it is PM8150 LDO17 plus GPIO 119).
- `qcom/`: upstream SM8150 audio references (`sm8150-wcd9340.dtsi`, the Xiaomi cepheus/raphael DTS files, the `qdsp6` driver, `sm8150.c` machine driver). Use them as templates when porting audio nodes into the flattened DTS.
- `build/audio_ref/stock_vendor_b/`: stock OxygenOS `tfa98xx.cnt` and `mixer_paths_tavil.xml` read from the phone's `vendor_b` partition. These are the source of truth for audio routes (parse the container with `hotdog-linux-bringup/scripts/inspect-tfa-container.py`).
- `ref/lineageos/`: LineageOS 24 guacamole build (boot/dtbo/vbmeta and the OTA zip). Useful for downstream behaviour, e.g. modem and call audio.
- `linux-v6.17.0-sm8150/`, `build/kernel_r*/`, `extracted_dtb/device.dts` (the live DTB dumped from stock Android via `scripts/extract_dtb.sh`), and `backups/dtbo_*.img`.

## Device-specific gotchas

- The PM8150B charger depends on kernel patch `0011` (SMB5 limit fix). Without it, `qcom_smbx` programs about 4.85 V float voltage. After any change to the charger or the `battery` node, read back `0x1070` (float voltage), `0x1061` (fast-charge current) and `0x1370` (input limit) from `/sys/kernel/debug/regmap/0-02/registers` before leaving the phone on a charger.
- The bq27411 `capacity` register is voltage-based and reads 0 / Critical with a loaded cell near 3.4 V even when `charge_now` says 30%; UPower powers the phone off on Critical. Treat Critical as real and get the phone onto the 5 V DCP charger (1.8 A); a USB 2 PC port (500 mA) does not keep up with the screen on.
- Charging policy lives in `guacamole-chgctrl` (device package, systemd unit), not the kernel: it sets `pm8150b-charger/input_current_limit` from the PD contract or BC1.2 type and suspends the input via `status` (write `0` to suspend, `1` to resume). Stop the daemon before experimenting with those files by hand, and never leave the input suspended (`echo 1 > .../status`). `/run/guacamole/charger` is the source-type indicator.
- The fuel gauge is `ti,bq27411` on `i2c@a80000`. Never add `monitored-battery` to it, because that lets the driver write the gauge's data memory.
- Never test Wi-Fi by unbinding/rebinding `ath10k_snoc` or by stopping/starting `remoteproc0` at runtime: the MSA region stays assigned to the modem, and a reboot from that state has dropped the phone into Qualcomm crashdump mode (recover with Power + Volume Up). Use a fresh boot for every Wi-Fi test.
- Debug ath10k on a fresh boot by adding `ath10k_core.debug_mask=0x300022` (BOOT, WMI, SNOC, QMI) to the boot image cmdline.
- UFS must stay at HS-G3 (kernel patch `0010`). At HS-G4 the link drops buffered writes silently (`OCS invalid` after UIC errors). After any suspected corruption, verify with `apk audit --system` and re-hash files after `echo 3 > /proc/sys/vm/drop_caches`.
- The WLAN firmware, board data, Bluetooth firmware and IPA firmware come from a LineageOS OTA. Before building `firmware-oneplus-guacamole`, run `scripts/extract_lineage_firmware.py ref/lineageos/<lineage zip> device/testing/firmware-oneplus-guacamole` to create the local tarball.
- Reboots with Wi-Fi on rely on `qcom,dload-mode` on the `scm` node (TCSR syscon at `0x1fc0000`, offset `0x13000`). Without it, the download-mode cookie stays armed and a reboot with Wi-Fi active can end in Qualcomm crashdump mode (recover with Power + Volume Up).
- USB tethering on the phone is the local `/etc/systemd/system/usb-internet.service` (default route via `172.16.42.2` on `usb0` plus public DNS). Its route metric must stay at 30000: NetworkManager adds 20000 to a connection's route metric when its connectivity check fails, so a lower USB metric (it was 1000) captured all traffic and DNS on a PC that was not forwarding, and the Wi-Fi check could never recover.
- Sensors run on the SLPI DSP through `hexagonrpcd` (served tree `/usr/share/qcom`, registry under `/var/lib/guacamole/sensors`) and `iio-sensor-proxy` (libssc). Both are locally patched aports in `device/testing/` (`hexagonrpcd`, `iio-sensor-proxy`), also copied into pmaports `main/`; build them with `pmbootstrap build --arch aarch64 <pkg>`. Never restart `hexagonrpcd` after it has attached to the sensor PD; the PD is created on the first attach only and a restart leaves the sensors dead until reboot. Phosh releases the accelerometer while the screen is off, so test rotation with the screen awake, and use `sudo monitor-sensor --accel` over SSH.
- Device packages that ship Hexagon `.so` files need `!strip !tracedeps` in `options`, or abuild fails on them.
- Run `sync` on the phone after every `apk add` and before any reboot (`ssh user@172.16.42.1 'sync; sudo sh -c "sync; systemctl reboot --reboot-argument=bootloader"'`; systemd 262 ignores the positional `reboot bootloader` form, the argument must be `--reboot-argument=`). An r10 kernel upgrade followed straight by `reboot bootloader` once left `/usr/lib/modules/<ver>/` pointing at freed inodes. No modules loaded on the next boot, so touch, audio, the DSPs and Wi-Fi were all missing.
- The local packages (`linux-postmarketos-qcom-sm8150`, `device-oneplus-guacamole`, `firmware-oneplus-guacamole`, `hexagonrpcd`, `iio-sensor-proxy`, `libcamera`, `pipewire-spa-libcamera`) are pinned to exact versions in `/etc/apk/world` on the phone (`pkg=ver`). Without the pins, a large `apk add` from the upstream repository (installing `plasma-mobile` did this on 2026-11-23) replaces them with the pmOS builds: the upstream `linux-postmarketos-qcom-sm8150` is 7.0.0, whose modules do not match the 6.17.0 kernel in `boot_b`, so the next boot has no touch, DSPs or Wi-Fi. The host package directory is registered as the first repository in the phone's `/etc/apk/repositories` (`http://172.16.42.2:8124`, signed with the pmbootstrap key `pmos@local-6acaa678.rsa.pub` installed in `/etc/apk/keys`), served with `python3 -m http.server --bind 172.16.42.2 --directory ~/.local/var/pmbootstrap/packages/edge 8124` on the host. With the server running, a new local build installs with `apk add pkg=newver`, which moves the pin; without it, apk only warns that the index is unreachable. A pinned version that no repository offers, or a package whose install script failed (`apk fix --simulate` lists it), makes every apk run end in `1 error` with exit code 1. The phone needs `http_proxy=http://172.16.42.2:8123` (a plain HTTP proxy on the host) for the upstream mirror when its own route has no DNS. The `.apk-new` left in `/etc/conf.d/guacamole-chgctrl` is the usual config merge, the live file keeps the user's `CHG_SDP_UA`.
- Rootfs repair: boot an image with `pmos.debug-shell` on the cmdline, then `nc 172.16.42.1 23`. In that shell, `losetup --show -Pf --direct-io=on --sector-size 4096 /dev/sda19` (`userdata`), `e2fsck -fy /dev/loopNp2`, `losetup -d`, `pmos_continue_boot`. Then restore any cleared package files: extract the APK over `/`, run `depmod -a`, check with `apk audit --system`, and run `udevadm trigger --action=add`.
- ABL splices the UFS `dtbo_<slot>` partition into whatever DTB it boots. The active slot's DTBO has been zeroed (the originals are in `backups/`). If boots hang silently with no early output, check this first.
- The Linux rootfs is a pmOS image on the `userdata` partition (UFS LUN 0, partition 19), with the boot and root subpartitions mounted through `loop0` and referenced by UUID in `/etc/fstab`. Stock Android stays on slot `_b`. `sdX` names are not stable: the six UFS LUNs probe asynchronously, so LUN 0 is not always `sda`. Use `/dev/disk/by-partlabel/` or SCSI addresses (`0:0:0:N`) instead.
- UFS uses 4096-byte sectors (`deviceinfo_rootfs_image_sector_size`).
- Cameras: the three rear sensors work (see "Cameras" in README.md); the front IMX471 does not answer on this unit, so its node and the `camss` `port@2` endpoint stay disabled. `camss` exposes nothing until every live endpoint's sensor has bound, so a dead sensor must be disabled on both ends. Test with `cam -l` and `cam --camera <dt path> --stream role=raw --capture=N --file=...` (`libcamera-tools`); camera numbers change between boots, use the path. A `CSID reset timeout` on the first session after idle means MMCX is at low SVS: the `camss` `required-opps` must stay. Prefer raw sessions for kernel testing; the software-ISP output has a padded stride (16128 bytes for 3992 pixels). Never write more than a few frames with `--file` into `/tmp` (3.6 GB tmpfs): a full run fills it and breaks Flatpak and anything else using temp files. Autofocus lives in the libcamera package (patch `0006`, `Af` in the tuning files) and needs a lit scene; debug it with `LIBCAMERA_LOG_LEVELS=IPASoftIspAf:DEBUG`. `device/testing/libcamera` is a copy of pmaports `temp/libcamera` plus the OnePlus sensor data; after editing it, copy it to the pmaports `temp/libcamera` directory and run `pmbootstrap checksum libcamera` as for the kernel.
- DisplayPort over USB-C: the connector carries a `displayport` altmode (svid 0xff01, vdo 0x1c46), the FSA4480 at `i2c@890000` 0x42 (enable on TLMM GPIO 100, active low) switches the SBU/AUX pair, and `displayport-controller@ae90000` is enabled with `data-lanes = <0 1>` and `power-domains = <&rpmhpd SM8150_MMCX>` (the upstream dtsi says `SM8250_MMCX`, which is index 6 = `MX_AO` on SM8150 and hangs the boot). A USB-C to DP cable (Realtek adapter) drives a monitor at 1920x1080 under Plasma Mobile; `typec_displayport` is a module and loads on attach. Because the display driver binds at about 14 s, an adapter attached at boot enters its altmode before any DRM connector exists and the hotplug is lost: the device package's `90-guacamole-dp-hpd.rules` runs `guacamole-dp-hpd` when the DRM card appears, which leaves and re-enters every active DisplayPort altmode (`echo 0/1 > .../port0-partner.0/active`). The same toggle is the manual remedy when `DP-1` stays `disconnected` with the altmode active. Unpowered adapters log `vbus vsafe5v fail`, which is harmless. DP audio (hotdog 0050–0052), docked charging and dock USB are untested.
- `pstore` is served by the cmdline `ramoops.*` parameters; the DT `ramoops@a9800000` node then fails with `-22` (duplicate), which is harmless. A hard reset (Power held 10 s) does not preserve ramoops; only panics and watchdog bites do.
- Large binaries (`*.img`, the TWRP zip, `stock_boot*.img`) sit in the repo root and are gitignored. Never commit them.
